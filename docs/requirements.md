# 要件定義書 — Trello風タスク管理アプリ

## 1. プロジェクト概要

| 項目 | 内容 |
|------|------|
| プロジェクト名 | Raise App — Task Management |
| 目的 | 学習用のTrello風タスク管理アプリを段階的に開発する |
| 対象ユーザー | 開発者自身（学習・個人利用） |
| 開発方針 | バージョンを重ねながら機能と技術スタックを拡張していく |

---

## 2. バージョンロードマップ

| バージョン | フロントエンド | バックエンド | 主な目的 |
|-----------|-------------|------------|---------|
| **v1** | React + Vite + TypeScript + TailwindCSS | Spring Boot + Gradle + PostgreSQL | DB構築・REST API・Reactデータ表示の基礎を理解する |
| **v2** | 同上 | 同上 | カード編集・カラム追加など機能拡張・UI改善 |
| **v3** | 同上 | 同上 + 認証 | ユーザー認証（Spring Security + JWT）を理解する |
| **v4** | 同上 | 同上 + デプロイ | 本番環境へのデプロイ・実用アプリとして完成 |

### 3.2 機能一覧

| # | 機能 | 詳細 |
|---|------|------|
| F-01 | カード追加 | 各カラムにテキスト入力でカードを追加できる |
| F-02 | カード削除 | カードの✕ボタンをクリックで削除できる |
| F-03 | カード移動 | ドラッグ&ドロップで任意のカラムへ移動できる。同カラム内での上下並び替えも可能 |
| F-04 | データ永続化 | ページをリロードしてもデータが消えない（localStorage使用） |
| F-05 | 優先度設定 | カードに「高・中・低・なし」の優先度を設定できる。色分けバッジで視覚的に区別する |
| F-06 | 期限設定 | カードに期限日を設定できる。期限超過は赤、2日以内は黄色で自動着色する |

### 3.3 非機能要件

非機能要件とは「システムが何をするか」ではなく「システムがどうあるべきか」を定義するものです。
実際のITシステム障害の多くはこの非機能要件の設計不足から発生します（性能不足によるダウン、セキュリティ不備による情報漏洩など）。

#### 性能

| # | 項目 | 内容 |
|---|------|------|
| N-01 | 応答速度 | カードの追加・削除・移動が1秒以内に画面に反映されること |
| N-02 | データ読込 | ページ読み込み時にlocalStorageからのデータ復元が即時完了すること |

#### 保守性
> 「後から修正・機能追加がしやすいか」。v2・v3への拡張を見据えた設計にすることが目的。

| # | 項目 | 内容 |
|---|------|------|
| N-03 | コンポーネント分割 | Board / Column / Card / AddCardForm に責務を分けて実装する |
| N-04 | データ管理の集約 | カードデータの状態（state）はAppコンポーネントで一元管理する |
| N-05 | 命名規則 | コンポーネント名はPascalCase、関数・変数名はcamelCaseに統一する |

#### 移植性
> 「別の環境・ブラウザでも同じように動くか」。

| # | 項目 | 内容 |
|---|------|------|
| N-06 | ブラウザ対応 | Chrome・Firefox・Edgeの最新版で正常に動作すること |
| N-07 | データ形式 | localStorageの保存形式をJSON文字列に統一し、v3以降のAPI移行を容易にする |

#### 拡張性
> 「将来の機能追加を妨げない設計になっているか」。

| # | 項目 | 内容 |
|---|------|------|
| N-08 | データ構造 | カードにidフィールドを持たせ、v4以降のDB設計に対応できる構造にする |
| N-09 | スタイル管理 | CSSをコンポーネント単位で管理し、スタイルの衝突を防ぐ |

#### セキュリティ（v1時点）
> v1はローカル動作のみのため本格対応は不要。v5の認証実装時に改めて設計する。

| # | 項目 | 内容 |
|---|------|------|
| N-10 | 入力値 | カードテキストの空文字登録を防ぐバリデーションを実装する |
| N-11 | XSS対策 | ReactのJSXはデフォルトでエスケープ処理されるため、`dangerouslySetInnerHTML`は使用しない |

| UC-06 | 期限を設定する | カードの期限バッジをクリックして日付を入力する | 対象カードが存在すること | 設定した期限日がカードに表示され、超過・近接の場合は色が変わる |

## 6. ER図（データ構造）

ER図（Entity Relationship Diagram）とは「データの種類と関係」を示した図です。v1ではDBは使いませんが、このデータ構造がv4以降のテーブル設計の基礎になります。

<!-- [変更] ER図：Cardエンティティにpriority・dueフィールドを追加（2026-10-30）
  理由：プロトタイプ確認でv1スコープに優先度・期限が追加されたため
-->
```
┌─────────────────┐          ┌──────────────────────┐
│     Column      │          │         Card         │
├─────────────────┤          ├──────────────────────┤
│ id (文字列)      │ 1      N │ id (文字列)            │
│ title (文字列)   │ ───────► │ text (文字列)          │
│                 │          │ columnId (文字列)      │
└─────────────────┘          │ priority (文字列)      │
                             │   ※ high/medium/low/none│
                             │ due (文字列 or null)   │
                             │   ※ YYYY-MM-DD形式     │
                             └──────────────────────┘

※ 1つのColumnは複数のCardを持つ（1対多の関係）
※ v1ではColumnは「未着手」「進行中」「完了」の3つ固定
```

### v4以降のDB移行イメージ

| v1（JSON） | v4（DBテーブル） |
|-----------|----------------|
| `column.id` | columnsテーブルの主キー |
| `column.title` | columnsテーブルのtitleカラム |
| `card.id` | cardsテーブルの主キー |
| `card.text` | cardsテーブルのtextカラム |
| `card.priority` | cardsテーブルのpriorityカラム（ENUM型想定） |
| `card.due` | cardsテーブルのdue_dateカラム（DATE型想定） |
| カードがどのcolumnに属するか | cardsテーブルの外部キー（column_id） |

> カードのドラッグ操作はCardコンポーネントにイベントを持たせ、ドロップ受け入れはColumnコンポーネントが担う。
